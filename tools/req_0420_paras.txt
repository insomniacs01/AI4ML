069: 1 文档介绍
070: 1.1 文档目的
071: 本文档用于定义 AI4ML 项目的产品目标、用户角色、系统边界、业务流程、功能性需求、数据需求、接口需求、非功能性需求以及验收标准，为后续设计、开发、测试、上线和持续迭代提供统一依据。
072: 本文档同时解决两个问题：
073: 清楚本项目到底要做什么、为什么这样做、哪些内容是重点。
074: 能够基于统一的需求口径继续推进实现，而不是只停留在“泛泛描述”和“概念性目标”。
075: 1.2 文档范围
076: 本文档覆盖以下两类需求：
077: 平台产品层需求：角色管理、任务录入、数据上传、AI 工作流、进度可视化、报告输出、代码查看、人机协同、社区沉淀与治理。
078: 执行底座集成需求：基于 MLZero 的本地任务执行、Provider 生命周期管理、运行产物保存、结果回写与日志追踪。
079: 本文档不展开描述 MLZero 内部算法实现原理，只定义本项目如何调用、约束、展示和管理 MLZero 的能力。
080: 为避免将“底座自带能力”与“本项目新增平台能力”混为一谈，本文档统一使用以下四类归属口径：底座原生能力、底座兼容性改造、我们的平台新增、我们的规划新增。
081: 1.3 读者对象
082: 本文档主要面向以下对象：
083: 项目组前端、后端、AI/Agent 开发人员
084: 课程汇报与需求评审人员
085: 测试与验收人员
086: 后续撰写概要设计、测试文档和用户手册的成员
087: 1.4 术语与缩写解释
088: 术语 / 缩写
089: 解释
090: AI4ML
091: 本项目名称，目标是构建 AI 驱动的低代码 / 零代码机器学习平台
092: MLZero
093: 当前选定的执行底座，用于自动完成表格机器学习任务
094: Agent
095: 负责某个阶段任务的智能体或阶段处理器，如需求解析、数据分析、模型选择等
096: Task
097: 平台中的一个机器学习任务对象，包含任务描述、数据集、状态与运行结果
098: Run
099: 任务的一次执行记录，包含日志、指标、产物和输出目录
100: Provider
101: 为 MLZero 提供模型推理能力的 OpenAI-compatible 服务
102: Token Ledger
103: 记录模型调用 Token 消耗、调用时间、调用用户、关联任务的账本
104: Quota
105: 用户可用的资源额度，可按 Token、调用次数或预算单位进行约束
106: Workflow
107: 从需求解析到训练评估、报告生成的一组可复用流程定义
108: Dataset Asset
109: 用户上传后进入平台管理或共享的数据集资产
110: Model Asset
111: 用户训练或发布后进入平台展示与治理的模型资产
112: 2 项目概述
113: 2.1 项目背景
114: AI4ML 项目面向教学、实验和原型验证场景，目标是降低机器学习建模门槛，让零基础用户可以通过自然语言描述需求并上传数据，由平台自动完成任务理解、数据分析、模型训练、结果解释和后续复用。
115: 要求不仅希望平台能够“跑通一次模型”，还强调以下能力：
116: 管理员能够管理用户角色、资源额度、数据集与模型资产
117: 零基础业务用户能够通过自然语言发起任务，并看到 AI 工作流进度
118: 有经验开发者能够在流程中进行人工干预、查看和修改生成代码
119: 平台需要具备流程图、架构图、状态流转图等完整图示，而不是只有纯文字
120: 2.2 产品定位
121: AI4ML 是一个分阶段演进的平台：
122: 对零基础业务用户，它是一个自然语言驱动的机器学习任务助手。
123: 对开发者用户，它是一个支持查看、干预、复用工作流的可控实验平台。
124: 对管理员，它是一个带有额度治理、资产审核和内容管理能力的平台底座。
125: 2.3 建设目标
126: 2.3.1 长期目标
127: 构建一个面向零基础用户、开发者用户和管理员三类角色的 AI4ML 平台
128: 支持需求结构化、Agent 化工作流、多阶段进度可视化、人机协同和社区化复用
129: 形成数据集、模型、工作流和报告等平台资产的沉淀与治理能力
130: 2.3.2 核心交付目标
131: 完成团队创建、成员邀请、角色分配、AI 连接配置、任务执行与结果沉淀的完整产品闭环
132: 支持自然语言需求录入、数据上传、自动工作流编排、结果回写与复用
133: 支持管理员进行成员管理、额度治理、AI 连接器管理和默认 AI 组合配置
134: 支持成员清晰查询各个 AI 在任务中的阶段进展，并查看关键代码产物
135: 支持成员按模块 / 阶段选择 AI；若不主动选择，则自动继承管理员默认 AI 组合
136: 支持管理员为各阶段配置默认 AI 组合，并统一治理可选连接器范围
137: 支持管理员通过导入不同的 Key、账号、Base URL 或连接配置接入多个 AI 连接器，而不是受限于单一 API 模型
138: 支持团队注册、成员邀请和“团队中至少保留 1 名管理员”的治理约束

580: 适用角色

582: 功能说明
583: 系统应以团队为基本组织单位，支持团队创建、成员邀请、角色设置与状态管理，并根据角色控制前端入口和后端接口权限。团队创建后创建者自动成为团队所有者，且系统必须保证团队始终至少有 1 名管理员。

587: business_user / developer_user：业务成员 / 开发成员

589: 平台账号仅用于身份认证与全局审计；团队内实际授权以 TeamMember 记录为准。

593: 系统应支持在任务开始前或执行中按阶段配置人工参与节点，并指定具体成员、角色或候选参与组。
594: 被配置为节点参与人的成员，可在权限范围内执行确认、补充、修改、驳回、转交或继续执行。

596: 主要流程

601: 目标用户重新登录或刷新后按新角色生效。
602: 业务规则
603: 普通用户不得访问管理员页面。
604: 角色控制必须同时作用于菜单入口和后端接口鉴权。
605: 角色变更、禁用、恢复操作必须有审计日志。
606: 系统必须阻止把最后一位管理员降级、禁用或移出团队。
607: 团队创建后创建者自动成为首位管理员。
608: 验收标准
609: 管理员可查看用户列表并修改角色。
610: 普通用户访问后台时会被拦截。
611: 修改角色后，页面功能入口发生变化并生效。
612: FR-ADM-0002 API Token / 资源额度管理
613: 属性
614: 内容
615: 编号
616: FR-ADM-0002
617: 优先级
618: P0
619: 交付要求
620: 本版必须交付
621: 适用角色
622: 管理员
623: 功能说明
624: 系统应支持管理员按团队成员管理 API Token 或等价资源额度，并在任务执行前、执行中对额度进行检查、扣减、预警和限制。额度控制应至少支持“按成员”维度，必要时可扩展到“成员-连接器”维度。
625: 主要流程
626: 管理员进入额度管理页面查看用户剩余额度、累计消耗和调用记录。
627: 管理员对用户执行充值、扣减、冻结、解冻等操作。
628: 用户提交任务后，系统先进行额度预检查。
629: 工作流执行过程中，每次模型调用写入 TokenLedger。
630: 当额度不足时，系统阻止继续执行并返回可读提示。
631: 额度核算规则
632: Token 消耗的首选数据源必须是模型服务返回的 usage.prompt_tokens、usage.completion_tokens、usage.total_tokens。
633: 若本地 Provider 不返回 usage，则必须使用与目标模型一致的 tokenizer 对输入输出进行离线复算，并记录 calculation_method = tokenizer_estimate。
634: 禁止使用“固定倍率估算”或“按步骤拍脑袋扣费”的方式代替真实 Token 口径。
635: 每条流水至少记录：用户 ID、任务 ID、阶段 ID、模型名称、输入 Token、输出 Token、总 Token、时间戳、核算方式。
636: 额度检查必须早于高开销阶段执行，避免任务跑到中途才发现不可用。
637: 管理员可按成员维度设置额度上限，也可按成员-连接器维度进行更细粒度限制。
638: 验收标准
639: 后台存在额度实体、充值 / 扣减能力和消耗流水页面。
640: 额度不足时系统能阻止任务进入高开销阶段。
641: 管理员能看到用户维度和任务维度的消耗明细。

1655: 6.4 接口设计原则
1656: 除 /api/health 以及团队创建 / 团队列表接口外，其余业务接口统一围绕 /api/teams/{team_id}/... 资源展开。
1657: 路由层保持轻量，业务逻辑下沉到服务层。
1658: 统一返回状态、消息和可追踪 ID，便于前端提示和问题排查。
1659: 后台接口必须接入角色鉴权与审计日志。
1660: 7 非功能性需求
1661: 7.1 易用性要求
1662: 零基础用户应能在少量页面内完成任务发起、数据上传、运行查看和结果理解。
1663: 页面文案需尽量使用业务可理解语言，而不是仅展示底层技术术语。
1664: 失败提示应可读，而不是直接暴露原始异常堆栈。
1665: 7.2 性能要求
1666: 健康检查、任务列表查询在本地环境下应在 2 秒内返回。
1667: 任务创建接口应在 2 秒内返回。
1668: 单个 CSV 上传在 100MB 以内应支持稳定完成。
1669: 工作流进度刷新建议采用轮询或流式更新，刷新间隔不超过 5 秒。
1670: 额度检查应在阶段执行前完成，避免高成本阶段空跑。
1671: 7.3 可靠性要求
1672: 任务创建、上传、运行三个关键环节必须有明确状态流转。
1673: 运行失败时必须保留日志、输出目录和错误摘要。
1674: Provider 异常退出后应支持再次检测和自动拉起。
1675: 7.4 安全性要求
1676: 管理后台必须进行身份认证与权限校验。
1677: 上传文件需校验类型、大小和文件名安全性。
1678: 用户代码编辑能力上线前，应增加执行隔离或最小权限控制。
1679: 日志、额度和审核记录不得被未授权用户访问。
1680: AI 连接器密钥必须加密存储，并按团队边界隔离访问。
1681: 7.5 可维护性要求
1682: 前端、后端、执行器、Provider 管理、文件存储必须分层。
1683: 需求文档、接口定义和目录职责应保持一致。
1684: 工作流状态模型与页面状态枚举需统一定义，避免前后端口径不一致。
1685: 7.6 可扩展性要求
1686: 未来应可扩展更多任务类型和模型 Provider。
1687: 数据中心、模型广场和工作流广场应基于统一资产模型扩展。
